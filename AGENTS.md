# Инструкции для AI-агентов

Правила для изменений в FineListener. Следуйте существующей архитектуре и делайте только относящиеся к задаче изменения.

## Проект

- Стек: React, TypeScript, MobX, Electron и Vite. Renderer использует MobX; Jotai остаётся в `electron/src/services/RecordingService.ts` через `jotai/vanilla`.
- `electron/main.ts` и `electron/src/` — main process, системные вызовы, IPC-контроллеры и сервисы.
- `electron/preload.ts` — типизированный безопасный мост между main и renderer.
- `renderer/src/` — React-приложение без прямого доступа к Node.js API.
- Feature-модули renderer находятся в `renderer/src/features/` и публикуют API через существующие `index.ts`.
- При изменении модели состояния renderer сверяйтесь с `docs/adr/0001-use-mobx-class-stores-in-renderer.md`; для предметных терминов используйте `CONTEXT.md`.

Перед изменением поведения найдите связанные вызовы и используемые абстракции. Сохраняйте изменения локальными; рефакторинг выполняйте только когда он нужен для задачи.

## Пользовательский текст, логи и комментарии

- Весь новый пользовательский текст пишите на английском: заголовки, подписи, кнопки, placeholders, tooltips, уведомления и ошибки.
- Новые сообщения в логах и новые комментарии в коде также пишите на английском.
- Не переводите существующий текст только потому, что изменяется содержащий его файл. Переводите или исправляйте старый текст только когда это входит в задачу или непосредственно требуется изменяемым поведением.
- Пользователю показывайте короткие нейтральные сообщения без внутренних технических деталей. Технические детали сохраняйте в developer logs.
- Комментарий должен объяснять неочевидное решение, ограничение или сложную derived/async-логику, а не пересказывать код.

## TypeScript и React

- Новый код пишите на TypeScript, кроме файлов, для которых в проекте уже используется другой язык или формат.
- Используйте функциональные React-компоненты; классовые компоненты не добавляйте.
- Объявляйте компоненты в существующем стиле через `React.FC<Props>` и используйте именованные экспорты. Экспорт может находиться в объявлении или в конце модуля.
- React-компоненты и файлы компонентов называйте в `PascalCase`. Для остальных файлов сохраняйте соглашение текущего каталога; не переименовывайте их только ради унификации регистра.
- Переменные и функции называйте в `camelCase`, типы и интерфейсы — в `PascalCase`, константы — в принятом рядом стиле.
- Для объектных структур предпочитайте `interface`; `type` используйте для union-типов, алиасов, utility-типов и случаев, где он точнее выражает модель.
- Выносите сложную бизнес-логику из JSX в функции или custom hooks.
- Используйте `useEffect` для синхронизации с внешними системами. Вычисляемые значения и обработку пользовательских событий выражайте без эффекта, когда это возможно.
- Разбивайте компонент, когда его части имеют самостоятельную ответственность или вложенность мешает чтению; не делите JSX по формальному числу уровней.
- Списки должны иметь стабильные ключи, связанные с идентичностью элемента.

## Состояние renderer

- Состояние приложения и общие UI-workflows держите в MobX class stores. `AppStore` в `renderer/src/stores/appStore.ts` объединяет специализированные stores; feature-local stores размещайте рядом с соответствующей feature.
- Передавайте один стабильный `AppStore` через React Context и `useAppStore`. Компоненты, читающие observable-состояние, оборачивайте в `observer`.
- Меняйте состояние store через его методы/actions; вычисляемые значения предоставляйте через getters. Переходы между несколькими stores координируйте в `AppStore`.
- В `useState` оставляйте только локальное состояние представления: открытие модального окна, временный ввод, фокус и подобные детали. Не дублируйте в React состояние MobX store.
- Для асинхронных операций сохраняйте проверку актуальности результата и освобождайте подписки при завершении жизненного цикла store. Доступ к preload API из store выполняйте через типизированный `RendererAdapter`.

## Electron и IPC

- Renderer взаимодействует с Node.js и ОС только через типизированный API из preload. Не импортируйте Node.js API и не вызывайте `ipcRenderer` в React-коде.
- Системную работу с файлами, процессами, диалогами и путями держите в main process за сервисной или controller-абстракцией.
- При добавлении IPC-возможности:
  1. используйте согласованное имя канала по соглашению ближайшего IPC-кода;
  2. типизируйте payload и результат;
  3. зарегистрируйте обработчик в соответствующем controller;
  4. откройте минимально необходимый метод через preload и обновите тип `window.api`;
  5. для IPC listeners возвращайте функцию очистки, удаляющую listener.
- Не передавайте renderer внутренние ошибки, пути или детали процессов без необходимости для UI.

## API и асинхронность

- Сетевую и интеграционную логику держите в существующих services/clients, а не внутри JSX.
- Обрабатывайте ошибки на подходящей границе: логируйте технический контекст и возвращайте UI безопасное сообщение.
- Не игнорируйте rejected promises и не оставляйте пустые `catch`.
- Сохраняйте существующие контракты отмены, очистки listeners и завершения процессов.

## UI/UX

- Для асинхронного UI учитывайте применимые состояния: loading, success, error и empty.
- Предотвращайте повторный запуск действия, пока оно уже выполняется, если операция не поддерживает параллельность.
- Необратимые или потенциально разрушающие пользовательские действия должны быть явно оформлены и запрашивать подтверждение, когда ошибку нельзя легко отменить.
- Сохраняйте используемые в проекте компоненты Mantine и существующие визуальные паттерны.

## Зависимости и область изменений

- Сначала используйте существующие зависимости, утилиты и абстракции.
- Добавляйте новую production dependency только когда задача не решается разумно текущим стеком; объясните необходимость в итоговом сообщении.
- Используйте ES imports. Следуйте существующим исключениям только там, где формат конфигурации или внешний инструмент этого требует.
- Не смешивайте функциональное изменение с массовым форматированием, переименованием или несвязанным рефакторингом.
- Сохраняйте пользовательские изменения в рабочем дереве и не перезаписывайте файлы вне области задачи.

## Проверка изменений

После изменения TypeScript или React-кода выполните и исправьте ошибки:

- `npm run typecheck`
- `npm run lint`

Дополнительно:

- запустите `npm run test`, если изменена бизнес-логика или поведение, покрываемое либо подходящее для тестов;
- запустите `npm run build`, если затронуты Electron boundaries, preload, сборка или конфигурация Vite;
- добавьте или обновите локальные тесты для исправленной критичной логики и нетривиального поведения, когда существующая тестовая инфраструктура это поддерживает.

Считайте работу завершённой, когда релевантные проверки прошли либо итоговое сообщение явно перечисляет проверки, которые нельзя было выполнить, и причину.
